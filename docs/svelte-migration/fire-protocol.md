# Fire and refreshed main protocol

The owned `POST /api/books/:id/fire` route belongs to the inferred Hono `AppType`, with shared runtime `FireBody`/`FireResult` validation. Membership and the existing per-person AI limiter run before generation. Existing model/business failures remain `{ok:false,error}`; successful card and file replies are discriminated by `mode`. File results intentionally contain server file metadata without an invented author: side-file consumers resolve the canonical room attachment. Provider calls, file/card creation policy and billing rates are unchanged.

The browser-safe card contract preserves older `data` charts and adds one to four aligned numeric series, Field delta/good/trend and primary LinkButton presentation. The normalizer retains existing aliases, graph limits and safe navigation rules. Book `msgCard` updates existing messages/origins without changing identity. Book `openSide` validates stored attachment metadata before notifying only the requesting person's room sockets; malformed metadata sends no notice. Person `focus` is independently validated by the personal-channel schema.

The historical `answers_ask` scalar SQL subquery yields `1` or `NULL`, whereas the wire field is an optional boolean. The stored-message producer converts only explicit `1`/`0`/`NULL` and preserves existing boolean/omitted values; malformed flags fail the existing row guard. This prevents approved replies from appearing as unloaded-parent queue requests without dropping whole history rows.

Regression sources: `rpc-routes.test.ts` exercises actual Hono validation/authorization/rate/output paths with a fake Fire service, new card DTO projection and personal focus wire parsing. `book-message-boundary.test.ts` exercises the actual Book open-file/live-card methods using fake SQL/socket receivers plus stored SQL-flag shapes. `room-store.test.ts` checks card identity, origins and cross-room isolation. `api.typetest.ts` checks request/response inference. These fixtures make no real AI calls and do not prove deployment, microphone permissions, browser live editing or Cloudflare persistence behavior; those remain integration gates.

Fire generation may outlive a person's membership. Each card/piece commit now reads current membership immediately before its synchronous Book mutation. The Fire service checks membership after generation too. Its file upload opts into an additional current-member guard before R2 storage and at the existing Book file-publication boundary after the R2 await. A confirmed denied publication removes only the newly allocated R2 key; it does not remove prior versions. Other storeFile callers retain their existing behavior. This is a late-authority boundary, not a transaction spanning D1, R2 and Durable Objects: an authorized commit completed before removal is retained, and a storage/delete transport failure remains an error rather than proof of cleanup. An ambiguous lost publication response never triggers deletion: the Book commit may already have succeeded.

`scripts/fire-authority.test.ts` invokes the actual Fire, Book and storeFile consumers with deliberately deferred model/storage doubles. It checks removal during card/file generation, direct Book calls after removal, removal during R2 storage with no file-index/message publication, and an authorized publication positive control. The AI module double is isolated in its own Bun process; the fixture is registered only in Worker typing. These sources do not establish real provider, R2 or Durable Object scheduling behavior.

Author checks for this boundary: isolated `bun test scripts/fire-authority.test.ts` passed 4 tests / 20 assertions (1.90s), then `bun test scripts/book-message-boundary.test.ts` passed 12 tests / 164 assertions (2.42s). Owned test/docs/config formatting and `git diff --check` passed. No compiler, real provider, Worker, R2, or browser was run for this follow-up.
