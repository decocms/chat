## Reader-owned remote opening

A remote App marker is room-authored content; displaying the document is not the reader's explicit Apps-open action. Native and default inline remote apps therefore ask the reader before loading the host SDK, fetching the UI resource, making the initial tool call, or activating a private document bridge. This applies regardless of `readOnlyHint`: app-only tools may be absent from the public tool list, and approving one annotated initial read would not authorize every subsequent call from the UI. The existing explicit fullscreen Apps-open path and room-local apps keep their prior behavior.

Each native frame has an independent opening question, separate from its later document-bound tool consent. Allow is checked against its captured frame, target/catalog identity and live document marker before continuing. Cancel performs no remote call and exposes Reopen; retry creates a fresh question/grant rather than replaying a cancelled operation. Prose and size edits retain an existing authorized frame. Removal, account/room departure and disposal make old controls inert before cleanup. The default app retains its existing one-question-at-a-time queue, with an abortable pending owner registered for pruning before any secure host exists; explicit Reopen creates a fresh iframe name and new reader question.

The controlled native DOM fixture uses explicitly `read_only:false` remote tools and checks zero SDK/UI/tool calls before approval, independent cancellation/retry, no replay on prose/size updates, fresh approvals after explicit reparenting, and stale pending Allow rejection before DOM flush. Default-app fixtures execute the actual consent, pending-owner and mount functions with controlled network/host dependencies, including removal/account/room abort and the unchanged explicit panel-open positive control. These fixtures do not prove real providers, native MessagePort behavior, or deployed browser safety; the existing real document-security browser gates remain required.
